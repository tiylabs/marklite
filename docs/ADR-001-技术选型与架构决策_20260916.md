## 1. 决策摘要

### 1.1 推荐路线

建议采用：

**Swift + AppKit 应用主体 + 系统文本编辑组件 + WKWebView 文档预览 + 独立文档领域层 + 原生文件与权限服务。**

- UI 主体由 AppKit 管理窗口、菜单、焦点、侧栏与分栏。
- 编辑器使用 NSTextView/TextKit；TextKit 具体版本经原型验证确定。
- Markdown 解析通过可替换接口接入，优先验证 cmark-gfm 及其 Swift 封装可行性。
- 预览使用本地 HTML/CSS 与少量 TypeScript 编译脚本，不建设完整 Web 应用。
- SwiftUI 可用于局部辅助视图，不拥有核心文档状态；没有明确收益时不引入。
- 领域层不依赖具体视图，也不直接暴露第三方解析器 AST。
- 原文件、恢复草稿、预览 DOM 和导出产物拥有不同生命周期，不互相冒充数据源。

这不是“所有功能都原生实现”：Markdown 排版交给 Web 引擎，系统文本与文件行为交给平台能力，应用负责协调与安全策略。

### 1.2 Rust + GPUI 的结论

**Rust + GPUI 是具有技术潜力、但当前产品基线下不建议作为默认实施路线的候选。**

主要原因不是 Rust 性能不足，也不是 GPUI 不能构建编辑器，而是本项目必须同时交付原生文本行为、双语辅助功能、沙盒文件授权、Web 排版、安全导出与多窗口生命周期。采用 GPUI 后，这些能力需要逐项核实和集成，不能把 Zed 的整套编辑器能力视为 GPUI 已经提供的现成组件。

如团队具备成熟 Rust/GPUI 经验，并愿意长期拥有自绘编辑器与平台适配层，GPUI 可以进入有时间盒的原型竞争；只有通过同一套硬门槛，才可替代推荐路线。

### 1.3 决策的有效前提

1. MVP 目标仍为 macOS 14+，没有已承诺的 Windows/Linux 交付日期。
2. 本地文件安全、输入法、辅助功能和导出正确性优先于跨平台代码复用率。
3. 不假定团队已经拥有生产级 GPUI 编辑器、Web 编辑器或原生文档框架。
4. 不假定团队擅长某种语言。实际技能、招聘成本和现有组件资产是决策复审输入。
5. 不为未来尚未确定的插件、协作、AI 或知识库功能提前建设平台。

如果这些前提变化，应复审本决策，而不是机械延续技术路线。

## 2. 从需求推导架构问题

### 2.1 硬约束与实现自由度

| 类别 | 必须保留的要求 | 不预设的实现方式 |
|---|---|---|
| 平台与体验 | macOS 14+、Finder 打开、系统菜单、快捷键、主题、VoiceOver | 不要求一定使用 AppKit 或 SwiftUI |
| 文档 | 同窗口多文档、全应用文件去重、显式移至新窗口 | 不要求使用 NSDocument |
| 编辑 | 纯文本、中文输入法、Unicode、独立撤销与查找替换 | 不要求使用 NSTextView、CodeMirror 或其他具体编辑器 |
| 预览 | CommonMark/GFM、有限安全 HTML、双向块级滚动 | 不要求使用 WebView，但实现必须达标 |
| 文件安全 | 手动保存、草稿恢复、外部变化与冲突保护、安全删除 | 不要求特定存储框架，但不能降低保证 |
| 导出 | 独立无脚本 HTML、完整分页 PDF、目标保护 | 不要求某个 PDF API |
| 本地化 | en、zh-Hans 完整交付，遵循系统应用语言 | 不要求特定资源格式 |
| 隐私 | 本地优先、默认不请求远程图片、不上传内容 | 不允许用远端渲染或云存储绕过难点 |

### 2.2 设计图带来的判断

主界面由紧凑标题栏、可隐藏侧栏、源码区、预览区组成，无复杂工作台和大量自定义可视化组件。

因此：

- 视觉实现不是主要技术风险，不能仅因“容易做出相似截图”选框架。
- GPU 自绘对本产品的价值主要取决于编辑和排版负载，而非普通三栏布局。
- 文件树应按需加载，不因采用某个 IDE 框架而引入项目索引、工作空间或标签页。
- 图中侧栏处于展开状态，不改变单文件默认隐藏的产品要求。
- 图片像素不作为布局单位；实际以逻辑尺寸、最小窗口、系统控件和辅助功能验证为准。

### 2.3 风险集中在哪里

本项目更接近“具备安全预览能力的本地文档编辑器”，而不是“带文件读写功能的 Markdown 页面”。主要风险为：

1. 多会话和异步任务导致错误文档被更新。
2. 保存、退出、删除、草稿清理之间出现数据丢失竞态。
3. 文档切换破坏输入法、撤销历史与焦点。
4. 不可信 HTML 或图片路径绕过安全边界。
5. 文件被外部原子替换、移动或改变权限时误判状态。
6. PDF 排版、预览位置恢复和多文档内存使用达不到要求。

技术选型应优先减少这些风险的自研面积。

## 3. 评估方法

### 3.1 先过硬门槛，再比较成本

以下能力不能通过其他项目的高分抵消：

- 输入法和 Unicode 正确性。
- 不丢失未保存内容，不静默覆盖冲突版本。
- 沙盒权限与内容隔离达标。
- en/zh-Hans、键盘和 VoiceOver 完整可用。
- 导出全文且不破坏任何受保护目标。
- PRD 规定的性能场景通过。

硬门槛未通过的路线，不进入正式实施，不以降低 PRD 安全要求换取上线。

### 3.2 门槛通过后的比较维度

按以下优先级比较：

1. **可靠性交付风险**：哪些关键行为可以复用成熟实现，哪些需要自研。
2. **长期维护成本**：语言与运行时边界、框架升级、系统适配、依赖安全修复。
3. **macOS 行为一致性**：文本、菜单、窗口、辅助功能、文件权限。
4. **性能与资源可控性**：输入延迟、解析调度、WebView 数量、内存生命周期。
5. **可扩展性**：是否能局部增加语法、主题、导出和平台能力。
6. **交付成本**：团队学习、测试矩阵、构建签名与故障诊断。

不使用未经实测的“性能快数倍”“包体只有若干 MB”或精确总分。定性矩阵用于暴露成本，不用于伪装客观排名。

## 4. 候选方案分析

### 4.1 方案 A：Swift + AppKit + 系统文本编辑 + WebKit

**组成**：AppKit 应用壳、NSTextView/TextKit、后台 Markdown 解析、WKWebView 预览、Foundation 文件服务。

**优势**：

- 文本输入、系统菜单、Responder Chain、窗口和辅助功能基础能力直接可用。
- 文件授权、保存面板、废纸篓、Finder 打开等不需要经过跨语言 IPC 才能调用。
- 预览复用浏览器排版，避免自行实现 HTML/CSS、表格和分页引擎。
- 主要业务语言统一为 Swift，Web 脚本只承担文档呈现与测量。

**代价与风险**：

- AppKit 命令式生命周期需要明确所有权，不能把所有逻辑堆入 WindowController。
- 系统文本组件仍需要 Markdown 高亮、撤销分组和文本位置映射集成。
- WebKit 随系统演进，需要在最低与当前支持系统上回归。
- 多文档容器不是默认“一文档一窗口”模型的直接套用。

**判断**：在 macOS 单平台前提下，自研风险面积最小，推荐作为基线。

### 4.2 方案 B：SwiftUI 主体 + AppKit 编辑器桥接 + WebKit

**优势**：声明式界面、轻量状态呈现和辅助界面开发便利，可继续使用系统文本组件。

**代价与风险**：

- 精细焦点、输入法组合、撤销管理器、菜单目标和窗口关闭仍要与 AppKit 协作。
- SwiftUI 视图身份变化不能导致编辑器重建；双向状态绑定不能复制出两套文本真相。
- 框架默认文档与自动保存语义未必匹配手动保存、多会话窗口的产品要求。

**判断**：可行，不因 SwiftUI 本身否定稳定性；但本项目核心复杂度并不由声明式 UI 消除。建议局部使用，而非强制让所有核心组件通过 SwiftUI 包装。

### 4.3 方案 C：Tauri + Rust 核心 + TypeScript/Web 编辑器

**组成**：Tauri 应用壳、Rust 文件与文档服务、CodeMirror 6 等 Web 编辑器、Web 预览，macOS 上使用系统 WebView。

**优势**：

- Web 编辑器生态适合 Markdown、语法高亮、查找与文本状态管理。
- Rust 适合编写可测试的文件、快照和权限策略代码。
- 若跨平台是近期目标，可共享较多 UI 与业务逻辑。
- 不需要像 Electron 一样随应用交付完整 Chromium 运行时。

**代价与风险**：

- 系统 WebView 的行为与版本受各平台影响，跨平台不是零成本。
- Web 文本交互与原生文本交互并不自动等价，需实测输入法、快捷键、无障碍和焦点。
- 文件授权、系统恢复等仍可能需要 macOS 专用桥接。
- Rust、TypeScript、平台适配与 IPC 协议形成更多升级边界。
- 不可信预览不能与有文件权限的应用 UI 混在同一可滥用的执行上下文中；应使用无桥接或严格受限的隔离预览上下文。

**判断**：近期明确跨平台、且团队具备 Rust/Web 经验时的优先备选；当前单平台下收益不足以抵消额外边界。

### 4.4 方案 D：Electron + TypeScript + Web 编辑器

**优势**：

- Chromium 版本随应用控制，前端行为相对一致。
- CodeMirror 等编辑器和测试工具成熟；Web 团队容易形成开发闭环。
- 可以复用 Web 排版、打印和前端语言资源体系。

**代价与风险**：

- 自带 Chromium/Node 及相关更新责任；资源基线、包体与安全更新负担通常高于系统 WebView 路线，具体数值必须实测。
- 必须隔离 main、preload、renderer 的权限；预览不应获得 Node 或通用文件 IPC。
- 原生文件授权、平台恢复、系统文本体验仍要专项集成。
- 不能仅因编辑器运行在 Chromium 中就假定通过全部 macOS 输入与 VoiceOver 要求。

**判断**：若团队已有成熟 Electron 文档编辑器资产，实际交付风险可能低于其他方案；没有此资产时，不作为本项目首选。

### 4.5 方案 E：Flutter + Dart + 文本编辑组件 + WebView/原生桥接

**优势**：统一 UI 和跨平台布局能力较强，自定义视觉表现可控。

**代价与风险**：

- 必须验证所选桌面文本组件的 Markdown 高亮、独立撤销、组合输入和辅助功能。
- 原生菜单、文件访问、Web 预览和 PDF 往往仍依赖平台适配与插件。
- 若最终同时依赖 WebView 和大量 macOS 原生接口，会形成 Dart、原生代码与 JS 三套边界。

**判断**：在已有 Flutter 桌面产品体系中可考虑；当前界面并不复杂到足以体现其主要优势，不推荐作为默认方案。

### 4.6 方案 F：Rust + GPUI

#### 4.6.1 GPUI 的定位

GPUI 是用于构建 GPU 加速应用界面的 Rust 框架，与 Zed 生态相关。它可以支撑复杂编辑器类应用，但必须区分：

- GPUI 提供的 UI、事件和平台抽象。
- Zed 产品中的文本模型、编辑器、语言服务、会话与其他上层实现。
- 第三方组件库额外提供的控件。

**使用 GPUI 不等于直接获得完整、可独立复用且许可适配的 Zed 编辑器。** 选定版本的公开 API、组件来源、输入与辅助功能覆盖、发行许可均须核验。不能因 Rust crate 可编译，就认定产品集成与商业分发条件已经成立。

#### 4.6.2 两种实际架构

**F1：GPUI 应用壳和源码编辑器 + 嵌入 WebKit 预览**

```text
Rust Document Core
  ├─ GPUI 窗口、侧栏、源码编辑与交互
  ├─ macOS 文件/权限/菜单适配
  └─ WebKit 原生视图桥接
       └─ HTML/CSS 预览、查找与打印
```

- 优点：保留浏览器 Markdown 排版生态，Rust 核心可复用。
- 代价：GPUI 与嵌入原生视图的布局、裁剪、DPI、焦点、滚动、辅助功能、全屏、销毁及线程约束必须逐项验证。
- 不能假设存在与所选 GPUI 版本兼容且生产就绪的 WebView 组件；若需自建桥接，其维护责任归项目。
- 若连源码编辑也改用嵌入 NSTextView，则 GPUI 主要只剩窗口与侧栏，需重新证明这层复杂性相较 AppKit 的收益。

**F2：GPUI 原生源码编辑 + GPUI 原生 Markdown 排版**

- 优点：运行时 UI 技术较统一，可控制排版与交互，不依赖 DOM 完成滚动映射。
- 代价：需要实现或集成表格、嵌套块、代码高亮、图片、链接、文本选择、可见文本查找、辅助功能语义与布局测量。
- 有限 HTML 仍需安全解析并转换为支持的原生内容；不能简单忽略 HTML 以宣称达标。
- HTML 导出需要另一路序列化；PDF 仍需分页排版或打印引擎，预览与导出容易出现语义和样式差异。

**针对本 PRD，若选择 GPUI，优先验证 F1；F2 的自研排版与导出范围明显超出一个轻量 MVP 的必要投入。**

#### 4.6.3 Rust + GPUI 的真实收益

- Rust 所有权与类型系统有利于约束内存和部分并发错误。
- 文本核心、解析、快照与文件策略可以形成无 UI 依赖的 Rust 模块。
- GPU 渲染有利于复杂自绘场景，适合需要长期掌控编辑器内核的产品方向。
- 若团队已有成熟 Rust/GPUI 组件和平台适配经验，可显著降低从零构建成本。

但这些收益不应被扩大解释：

- 内存安全不等于保存事务正确、无误删或无路径穿越。
- GPU 加速不等于解析、文件 I/O、图片解码、PDF 分页更快。
- Rust 不自动消除异步逻辑竞态；FFI/unsafe 边界仍需专项审查。
- UI 框架具备其他平台能力，不等于本应用的权限、导出和输入体验可以直接跨平台。

#### 4.6.4 必须先验证的专项风险

| 风险 | 需取得的证据 |
|---|---|
| 输入法与编辑核心 | 中日文组合、候选定位、Emoji/组合字符、撤销分组、跨窗口迁移实测 |
| 辅助功能 | 编辑文本语义、选区、菜单、目录树、错误提示在两种语言下的 VoiceOver 实测 |
| WebKit 嵌入 | 双栏缩放、全屏、焦点切换、触控板惯性滚动、视图释放和线程边界实测 |
| 平台集成 | Finder 请求路由、系统菜单、文件面板、沙盒授权、废纸篓与应用语言选择 |
| 组件复用 | GPUI 与候选组件的版本、公开 API、许可证、传递依赖及升级验证 |
| 维护成本 | 从一个锁定版本升级到另一个版本的演练、适配改动清单与回归时间 |
| PDF | 完整分页、链接、文字可选择性、长代码与表格验证，不能只导出屏幕截图 |

**进入正式实施的条件**：以上证据达标，团队明确承担编辑器与 macOS 桥接维护，并证明整体成本可接受。若失败，先关闭原型风险，不将半成品混入正式架构。

## 5. 横向比较与决策理由

下表的“低/中/高”表示当前基线下的相对集成或维护风险，不是框架的通用质量评级。

| 维度 | A AppKit | B SwiftUI 混合 | C Tauri | D Electron | E Flutter | F GPUI + WebKit |
|---|---|---|---|---|---|---|
| 原生文本行为集成风险 | 低 | 低至中 | 中 | 中 | 中至高 | 高，取决于编辑器资产 |
| macOS 文件/窗口集成风险 | 低至中 | 中 | 中至高 | 中至高 | 高 | 高 |
| Web 排版与导出集成风险 | 中 | 中 | 中 | 中 | 中至高 | 高，含嵌入桥接 |
| UI/权限跨边界维护负担 | 中 | 中 | 高 | 中至高 | 高 | 高 |
| 资源占用预期 | 较可控 | 较可控 | 较可控 | 需重点验证运行时基线 | 需实测 | 自绘潜力高，混合后需实测 |
| 近期跨平台复用潜力 | 低 | 低 | 高 | 高 | 高 | 中，取决于版本与桥接 |
| 当前需求的综合建议 | 首选 | 局部采用 | 条件备选 | 有团队资产时备选 | 非首选 | 研究性备选 |

所有方案都必须自行设计安全保存与恢复；“AppKit 集成风险低”不意味着其默认行为自动满足产品要求。

推荐 A 的核心依据是：它把最多的高风险系统行为交给直接可用的平台组件，同时仍保留 Web 排版生态。放弃的主要收益是较高的跨平台 UI 复用率和自绘引擎的完全控制权；这些都不是当前 MVP 的核心目标。

### 5.1 条件变化时如何重新选择

| 新条件 | 应重新评估的路线 |
|---|---|
| Windows/Linux 已列入近期交付，并接受平台行为差异 | Tauri、Electron |
| 团队已拥有通过输入法/无障碍验收的 GPUI 编辑器与桥接 | Rust + GPUI |
| 团队高度 Web 化，原生团队无法配置 | Electron/Tauri 原型与原生学习成本的实际比较 |
| 产品变成大型可编程编辑器，自绘成为核心竞争力 | GPUI，以及成熟编辑器内核方案 |
| 仅希望未来可能跨平台，没有排期 | 维持当前路线，保持领域边界，不提前双语言化 |

## 6. 与 UI 框架无关的目标架构

### 6.1 模块化单体，而非微服务或插件平台

```text
应用呈现层
  窗口 / 侧栏 / 编辑器 / 预览 / 菜单 / 临时提示
                │ 用户命令与状态投影
                ▼
应用协调层
  Open / Save / Close / MoveSession / Trash / Export
                │
                ▼
领域层
  DocumentSession / WindowSession / FileIdentity
  SavedBaseline / DiskBaseline / Conflict / RecoveryState
                │ 通过窄接口调用
                ▼
基础设施适配层
  文件系统 / 权限 / 监控 / 解析 / WebView / 导出 / 草稿存储
```

规则：

- 领域层不依赖 AppKit、GPUI、DOM 或具体解析器 AST。
- UI 不直接进行磁盘写入、授权、HTML 清洗和删除。
- 应用协调层是多步骤操作的入口，不允许视图各自拼接保存与关闭流程。
- 预览是编辑缓冲区的派生投影，不是内容数据库。
- 初期按目录与 target 隔离职责；只有测试、复用或编译边界确有需要时再拆 package/crate。
- 不为“可扩展”引入插件 ABI、事件总线、依赖注入容器或全局服务定位器。

### 6.2 权威状态与所有权

| 对象 | 拥有内容 | 明确不拥有 |
|---|---|---|
| 全应用文档注册表 | 会话注册、实际文件去重、窗口归属协调 | 每个视图的一份文本副本 |
| DocumentSession | 文本、撤销、版本、基线、冲突、资源授权引用、阅读状态 | 一个固定窗口的生命周期 |
| WindowSession | 有序会话 ID、活动会话、根目录、侧栏状态 | 文档缓冲区副本 |
| 编辑器适配器 | 系统文本机制及与权威模型的同步 | 与文档不同步的第二套持久状态 |
| PreviewController | 当前绑定、DOM、临时查找高亮、几何映射 | 保存基线和源文件写权限 |
| RecoveryStore | 草稿快照、元数据、清理代次 | 自动覆盖原文件的权力 |

文本存储可由编辑器后端承载，但必须属于会话所有权范围。不要同时维护可独立修改的 SwiftUI String、NSTextStorage 与领域缓冲区。

每个会话只属于一个窗口；移动会话改变归属，不复制内容和撤销栈。预览可以释放，后台未保存内容和独立撤销历史不可以因缓存淘汰而丢失。

**文档控制器归属（D10）**：采用自有 `DocumentSession` + 应用级协调器，**不继承 `NSDocument`/`NSDocumentController` 的文档生命周期**。理由：同窗口多会话的权威状态、保存事务、冲突与草稿协议（§7）已完整定义，而 `NSDocument` 的默认生命周期（自动保存、一文档一窗口控制器、内建关闭确认）需逐项关闭或绕过。保留该分支的风险是不对称的：反转将影响多个核心设计章节，而它附带的收益可用三个独立系统 API 以更小代价取得。

| 需要的能力 | 替代实现 |
|---|---|
| 最近打开菜单与 `Clear Menu` | `NSDocumentController.shared.noteNewRecentDocumentURL(_:)` 写入系统最近列表；**无需 NSDocument 子类** |
| 窗口恢复 | `NSWindow.isRestorable` + `restorationClass` 实现 `NSWindowRestoration` |
| 文件协调与外部变化 | 直接使用 `NSFileCoordinator` / `NSFilePresenter`（§7.3 已采用） |
| 文件类型关联 | 打包配置声明支持扩展名，Finder 请求经统一打开入口 |

约束：最近打开、窗口恢复与文件关联**不得因不使用 `NSDocument` 而缺失**；最近打开记录不构成访问凭证。全应用只有一套可写文档模型，`NSDocumentController` 仅用于「写入最近打开列表」这一项系统服务，不接管打开、保存、关闭与确认流程。

**判脏机制（D11）**：按固定块（初值 64 KB）维护摘要树，在 `NSTextStorage.didProcessEditing` 中按 `editedRange` 只重算受影响叶块及祖先路径；判脏 = 当前根摘要 ≠ 基线根摘要，**O(1) 同步精确**，脏状态只有 `clean / dirty` 两态。

PRD E-04 要求未保存状态由内容相对保存基线的差异决定，且撤销回已保存内容须恢复已保存状态（AC-06）——这排除了 `contentRevision == savedRevision` 与撤销计数器两种廉价实现。若改用异步全文比较，则会引入 `checking` 中间态，迫使每个危险操作（关闭、删除、保存、退出确认）在「读到陈旧 clean」与「保守误判为脏」之间二选一。摘要树消除这一整类问题，并顺带为草稿协议提供两项依据：内容未变则跳过检查点；大文档分块增量快照复用同一分块边界。摘要使用加密学摘要以消除碰撞风险。

### 6.3 并发与过期结果隔离

- UI 与会话状态提交在明确的串行执行上下文中完成。
- I/O、解析、资源解码使用后台执行器；Swift 中创建 Task 不等于自动离开主 actor。
- 同一文档的保存/重载等磁盘操作串行化；跨文档受控并发。
- 异步任务携带 `documentID + contentRevision + operationID`。
- 预览和目录枚举额外携带绑定代次或根目录代次；接收方校验当前归属。
- 取消任务与丢弃过期结果同时存在：前者节省资源，后者保证正确性。
- 解析器不支持中断时，必须以任务合并、队列上限和最大输入限制控制成本；不能声称已经实现中途取消。

语法高亮、预览、草稿分别调度，避免一个慢任务拖住所有链路。普通渲染先使用约 120–180 ms 合并触发，是否满足 P95 指标由实测决定。

## 7. 数据安全设计

### 7.1 核心不变量

1. 同一实际文件至多有一个可独立编辑的会话。
2. 原文件只在显式保存或明确冲突覆盖后写入。
3. 草稿成功不等于原文件保存成功。
4. 保存完成只能确认该次快照，不能清除随后输入的脏状态。
5. 放弃修改与会话关闭、草稿清理必须具有一致的完成语义。
6. 删除存在受影响脏会话时必须中止，不替用户保存或放弃。
7. 导出绝不覆盖源文档或任何已打开文档的实际文件。
8. 未经授权的资源不能因解析、预览、查找或导出而发起访问。

### 7.2 保存事务

```text
捕获不可变快照与基线
 → 获取目标操作资格，校验权限和文件身份
 → 检查磁盘当前版本
 → 有冲突则停止，进入用户决策
 → 在目标适当位置生成临时文件
 → 核验写入成功、重新检查目标与基线
 → 使用平台安全替换机制提交
 → 更新该快照对应的保存基线
 → 与当前缓冲区比较，更新脏状态与草稿
```

- 保留 UTF-8 BOM 和约定的换行策略；不意外改变末尾换行。
- `revision` 用于排序，不单独用于判脏；撤销回相同已保存内容应恢复干净状态。
- 内容比较可使用指纹与必要的内容比较组合；避免每次按键同步全篇哈希。
- 原子替换保证目标不会暴露半份新内容，不等于已经保证断电持久性或完全阻止外部竞争。
- 需明确临时文件位置、权限/元数据保留、同步策略和失败清理；最终实现以系统机制与目标文件系统验证为准。
- 文件协调不能锁住所有不协作外部程序。对无法消除的提交窗口应记录残余风险，采用尽可能窄的提交窗口、提交后检查和恢复快照，而非承诺绝对原子比较交换。

### 7.3 实际文件身份与外部变化

不能只以路径字符串去重。结合规范化路径、符号链接解析、文件系统资源标识及磁盘内容基线判断。

特别区分：

- 两条路径指向同一文件，包括可识别的硬链接别名。
- 原路径上的文件被 Git 等替换为新对象。
- 原文件移动后路径失效，但可定位到新路径。
- 删除链接节点与删除链接目标。

文件事件只表示“需要复核”，不是内容已变化的充分证据。系统自身写入事件通过操作记录去重，但不能因此忽略紧接着发生的外部写入。

### 7.4 关闭、退出与删除

关闭采用显式状态机：

```text
待处理 → 无修改直接关闭
      → 有修改 → 保存 → 成功关闭 / 失败保留
              → 放弃 → 使旧草稿写入失效并关闭
              → 取消 → 中止剩余关闭流程
```

- 批量关闭按 PRD 逐项完成，前面已经关闭的会话不因后续取消而复活。
- 清理草稿前先使旧备份任务失效；持久化放弃代次或等价标记，防止迟到任务恢复已放弃内容。
- 删除流程与关闭流程分离。有脏会话时仅阻止并定位，不调用“放弃并关闭”。
- 删除确认之后，执行前重新检查目标身份、相关会话状态和权限。
- 应用内部使用短期操作预留/提交屏障协调新增编辑与删除，避免预检后用户输入使干净会话变脏；不在等待确认时长时间锁住编辑器。
- 检测到外部路径竞态或无法确认目标身份时，保守中止操作（fail closed），保留会话与缓冲区，不以永久删除或猜测目标身份兜底。

### 7.5 恢复存储

首版采用应用容器内的版本化文件格式即可，不需要数据库：

- 每个 documentID 独立保存草稿、源引用、基线、版本与时间。
- 原子更新快照，包含长度/校验信息；写入失败保留上一个有效快照。
- 停止输入约 2 秒备份，持续输入至少每 10 秒检查点；后台会话遵循同样规则。
- 格式包含 schemaVersion，升级有迁移与损坏回退策略。
- 恢复时验证权限与磁盘基线；不匹配时作为恢复副本打开。
- 成功保存后的清理不能删掉较新编辑的检查点。
- 对磁盘满、进程终止、快照损坏、迟到任务和明确放弃分别做故障注入测试。

## 8. 编辑、渲染与资源隔离

### 8.1 编辑器与语法高亮

- 纯文本编辑，关闭不符合 PRD 的智能替换。
- 高亮只改变展示属性，不进入撤销栈，不整体重建文本视图。
- 输入法组合期间不强行重设选择或替换缓冲区。
- 全部替换作为单一可撤销操作。
- 明确 UTF-8 字节、UTF-16 索引、行列与用户感知字符之间的转换；维护统一映射工具和夹具。

优先复用解析器提供的范围与轻量词法信息。首版不必同时引入 Tree-sitter、另一套 Markdown parser 和自研正则解析器；只有性能数据证明有必要时，才增加独立增量高亮引擎。

### 8.2 解析器选择

`MarkdownEngine` 返回与第三方解耦的结果：**块语义、内联树、源码范围、资源引用与诊断**。

关键约束：输出是**结构化 AST，不是 HTML 候选字符串**。先用解析器的 HTML renderer 生成字符串再整体清洗，等于主动丢弃结构信息、把可信 AST 降级为不可信文本，然后付出额外代价洗回来。PRD R-01 只要求“经安全清洗的**有限** HTML”，真正不可信的仅 `HTML_BLOCK` / `HTML_INLINE` 两类节点，不可信输入面远小于“整份渲染后的 HTML”。

候选范围：

| 路线 | 候选 | 必验项 |
|---|---|---|
| Swift/原生 | cmark-gfm、swift-markdown 封装路线 | GFM 子集、源码范围、C/Swift 边界、取消策略 |
| Rust | comrak、pulldown-cmark | 所选版本的扩展、范围语义、HTML 输出及取消成本 |
| Web | markdown-it 等 | CommonMark/GFM 实际兼容、source map、后台 Worker 与安全输出 |

这些是评估候选，不是已确认完整满足需求的依赖清单。源码范围在表格、嵌套列表、软换行和 HTML 块中的精度必须通过夹具证明。

### 8.3 预览安全流水线

```text
不可信 Markdown
 → 后台解析为 AST
 → 可信节点：按白名单直接安全序列化
 → raw HTML 节点：子集解析 + 白名单重建
 → 标签/属性/协议白名单与资源重写
 → 生成受控安全内容
 → 更新预览正文
 → 受控高亮、查找和块测量
```

**清洗的执行位置**：采用原生两层实现（详见 D09）——`SafeDocumentSerializer` 从 AST 直出安全内容，`RawHTMLSanitizer` 仅处理两类 raw HTML 节点。两层均为 `MarkliteCore` 内的纯函数，热路径零 IPC。DOMPurify 等成熟清洗器**降为阶段 0 对照实现**，用于交叉校验输出一致性；若对照证明原生实现无法达到等价安全水平，才回退到受限 WebView 清洗。

以下安全约束不因清洗后端选型而变：

- 必须使用应用定制的标签/属性白名单，采用白名单重建而非黑名单过滤；无法确定安全时降级为转义文本，不放行。
- 不通过正则替换实现 HTML 安全，不把 CSP 当作清洗替代品。
- 内容在插入活动 DOM 前完成清洗与 URL 重写；连清洗阶段也需验证不会发起网络请求。
- 移除脚本、事件属性、表单、iframe、base、外部样式和用户提供的任意样式。
- 防止 ID/name 冲突、DOM clobbering 和文档内容伪造应用控件；应用控制 UI 放在文档区域之外。blockID 由应用按 AST 结构写入，**天然不经过用户内容**，不依赖清洗器保留内部属性。
- 应用脚本使用隔离执行环境与窄桥接；隔离环境不意味着 DOM 自动可信。
- 桥接只允许固定消息类型和参数，校验绑定会话、来源与导航状态；不得暴露通用路径读写或任意脚本执行。
- CSP、导航拦截和资源代理形成多层防线。默认不允许直接 http/https 图片加载。
- 若回退到受限 WebView 清洗，必须保留：清洗壳 CSP 禁止网络/图片/字体/框架/对象及页面脚本；未清洗内容只在惰性/脱离 DOM 中处理。

### 8.4 本地与远程资源

本地资源解析使用会话授权引用和受控资源 ID，不把用户目录直接开放给 WebView。

- 规范化、符号链接解析与授权边界检查；防范检查后路径变化，尽可能通过稳定句柄读取并验证身份。
- 共享授权通过引用计数或等价租约管理，关闭目录不提前撤销文档仍需的权限。
- 远程图片只能由显式授权的会话触发下载；重定向逐跳校验协议和策略。
- 不自动发送环境 Cookie 或凭据，不绕过证书错误；网络上下文与会话权限隔离。
- 覆盖 srcset、CSS URL、SVG 外部引用等旁路，不能只拦截 img src。
- 限制响应字节、解码像素、超时和缓存总量；SVG 不作为可执行文档加载。
- 导出只能使用允许访问的资源，不通过后台导出偷偷扩大权限。

### 8.5 滚动与查找

- 同步按源码块与 DOM 块映射，块内插值，比例仅为回退。
- 程序跟随与用户滚动明确区分，以序列号/来源标记防止反馈循环。
- 更新前记录顶部锚点，更新后恢复；图片高度变化后重新测量。
- 块 ID 不依赖永不变化的行号，结合范围、结构和邻近匹配保留锚点。
- 预览查找遍历展示文本并构建到 DOM range 的映射，处理跨文本节点匹配；不能只逐节点查找，也不能以原始 HTML 字符串计数。
- 重新渲染后重建查找结果；临时高亮不得进入 HTML/PDF 导出。

## 9. 导出架构

采用独立导出任务，输入为启动时的不可变文档快照和资源策略快照。

### 9.1 HTML

复用语法与样式生成能力，重新构建安全文档，内嵌允许访问的图片，不直接序列化当前预览 DOM。输出不包含应用脚本、桥接、私有协议地址和查找标记。

### 9.2 PDF

优先验证 WebKit 打印流程与平台打印能力。单一 `createPDF` 类 API 的存在不等于已满足 A4 分页、页边距和长表格要求。

- 独立导出渲染上下文，使用打印样式和固定页面设置。
- 等待受控资源达到成功或明确失败状态后输出。
- 验证多页、链接、可选择文字、长代码、超宽表格和超高块。
- 若主路线不能达标，单独评估本地 PDF 引擎的体积、许可证与样式一致性；不在无评审情况下加入远程服务或庞大浏览器运行时。

### 9.3 目标提交

导出使用与保存类似的临时生成、身份保护、覆盖确认和最终提交机制，但不改变文档保存基线。生成后重新检查目标是否被其他会话打开、是否发生替换；失败或取消保留原目标。

## 11. 性能与资源预算

### 11.1 直接继承的验收指标

测试基线：M1、8 GB、SSD、macOS 14+；MB 按 1,000,000 字节计算。

- 100 KB 内文档，停止输入至稳定预览 P95 ≤ 300 ms。
- 1 MB 内文档，从确认打开至可编辑 P95 ≤ 1 秒。
- 常规输入不出现连续超过 50 ms 的明显主线程阻塞。
- 验证 20 个约 100 KB 文档、五个单文档窗口与连续 30 分钟使用。
- 验证至少 10,000 项目录，未展开目录不递归扫描。
- 大文件遵循 PRD：≤1 MB 完整体验；>1 至5 MB 降频；>5 至20 MB 提示并默认编辑；>20 MB 拒绝打开，不丢弃编辑中已存在的内容。

### 11.2 资源策略

- 默认每个窗口仅为活动预览持有运行中的 WebView；后台预览暂停或释放。
- 导出上下文使用有上限队列，避免导出风暴产生无界 WebView。
- 编辑缓冲区和撤销历史按会话保留，不能作为普通缓存淘汰。
- **渲染管道并发（D12）**：解析与安全序列化共用同一个有界可取消执行器，并发为**每窗口 1、全应用上限 2**，调度按**活动文档 > 导出/后台任务**的优先级而非 FIFO；不设全应用单清洗槽。每会话只保留最新待处理快照，避免每次输入积压一个任务。
- 单槽会与多窗口场景冲突：窗口 A 处理大文档时窗口 B 的小文档编辑将排在其后（队头阻塞），使 ≤100 KB 文档的 P95 门槛无法成立，而单槽 + 可取消只能取消待执行任务。因此 P95 指标的可测条件为「单窗口活动文档、无并发大文档任务」；后台会话不渲染预览，不参与预览竞争。
- 图片缓存按字节和解码成本限额，不只按文件数量。
- 不在没有数据时承诺固定内存数字；阶段 0 测量进程及 Web 内容进程的基线和增量，再设明确回归阈值。
- 记录 P50/P95、主线程停顿、峰值内存、关闭后资源释放和版本丢弃次数；日志不记录文本和未脱敏路径。

## 12. 维护与扩展策略

### 12.1 依赖管理

- 锁定编译器/构建环境与第三方版本；提交 Package.resolved、适用的 JS/Cargo 锁文件。
- 记录直接及传递依赖许可证、分发资源与通知要求；尤其区分 GPUI 框架、Zed 代码和第三方组件的许可边界。
- 依赖升级单独提交，包含安全夹具、性能样例、最低系统回归和回退方案。
- 不直接依赖私有 API；必须使用的 FFI/底层调用集中封装并测试。
- 第三方库通过窄接口使用，UI 不导入其 AST、文件策略不依赖其错误文案。

### 12.2 本地化与可访问性

- 系统应用语言决定 UI，英文回退，不引入应用内语言设置。
- 使用参数化文案、复数和稳定键；内部状态不依赖翻译文本。
- CI 检查两种语言键与占位符，不以英文回退掩盖漏译。
- 两种语言均验证菜单、错误、文件操作、恢复和 VoiceOver。
- 窄窗口使用经验证的原生导航策略，不自动改变正文视图模式；临时导航可用 Esc 关闭并返回正确焦点。

### 12.3 扩展边界

| 后续能力 | 应扩展的模块 | 不应修改的核心 |
|---|---|---|
| 数学公式、Mermaid | Markdown 扩展、受控渲染资源、安全策略 | 保存与关闭事务 |
| 文档大纲 | 块级结构与导航投影 | 编辑文本所有权 |
| 自定义字体/主题 | 编辑配置、CSS 主题 | 文档编码与脏状态 |
| 图片粘贴 | 受控资源写入、可撤销源码插入 | 通用文件授权边界 |
| 文件对比 | 磁盘/保存基线与差异呈现 | 冲突保护规则 |
| 可选自动保存 | 保存策略与冲突协调 | 草稿和原文件的区分 |
| 新平台 | 新平台适配层；重新评估共享核心成本 | 文档语义和安全不变量 |

不承诺跨语言零成本复用。未来平台扩展可以移植领域逻辑或抽取共享核心，但不能用此可能性合理化首版不必要的 Swift/Rust 双核心。

每项原型记录：代码提交、锁定依赖、系统与硬件、夹具版本、步骤、原始结果和残余风险。GPUI 或其他候选不接受比推荐方案更宽松的门槛。

### 13.2 原型竞争的范围控制

先完成推荐路线的关键纵向切片；只有团队资产或产品路线提供明确理由时，才启动另一候选的同范围原型比较。原型时间盒由负责人按人员能力确认，不在缺乏团队信息时虚构工期。

比较切片至少包括：打开两个文件、中文输入、撤销、保存中编辑、会话移窗、预览更新、受控图片、分页 PDF。不能用一张静态三栏截图代表完成验证。

### 13.3 正式实施顺序

1. 建立文档状态、文件身份、保存事务和测试夹具，同时完成编辑/预览原型。
2. 单文档安全闭环：打开、输入、预览、保存、关闭；从首次 UI 起双语，从首次渲染起安全隔离。
3. 多文档与恢复闭环：切换、移窗、后台草稿、外部冲突、目录导航与会话恢复。
4. 文件操作、查找、受控资源与导出；删除依赖可靠的跨会话状态与草稿协调。
5. 性能、辅助功能、安全回归、签名公证与发布。

这是风险优先的实现顺序，不允许为了尽快展示文件树而提前交付尚无可靠保护的删除功能。

## 14. 决策记录

| ID | 决策 | 原因 | 代价/复审条件 |
|---|---|---|---|
| D01 | 当前采用 macOS 原生主体 | 减少系统行为自研与桥接 | 近期跨平台承诺变化时复审 |
| D02 | 预览使用 Web 排版 | 满足 GFM、有限 HTML 和导出复用 | 必须维护安全边界和系统 WebKit 回归 |
| D03 | 文档与窗口解耦 | 多文档、移窗、恢复的正确性基础 | 增加显式协调层，但所有路线均需要 |
| D04 | 使用模块化单体 | 降低开发与调试复杂度 | 模块变大后按真实边界拆分 |
| D05 | UI 无文件写权限入口 | 集中校验、事务与审计 | 所有写操作经过应用服务 |
| D06 | 草稿与原文件严格分离 | 满足手动保存与恢复语义 | 需要任务代次、迁移和损坏处理 |
| D07 | Rust+GPUI 为条件备选 | 自绘与 Rust 收益尚不能抵消当前集成风险 | 团队资产、实测证据或产品方向变化时复审 |
| D08 | TextKit/解析器/PDF 具体实现留给阶段 0 | 避免未经验证的 API 假设变成架构锁定 | 门槛通过后以补充 ADR 固定。NSDocument 部分已由 D10 结清 |
| D09 | 安全清洗采用原生 AST 直出，DOMPurify 降为对照 | 不可信输入面仅两类 AST 节点；避免把可信结构降级为文本再洗回 | 自研清洗组件缺公开审计历史，见 §15；对照不一致或安全不达标则回退受限 WebView 清洗 |
| D10 | 文档控制器采用自有 DocumentSession，不继承 NSDocument 生命周期 | 权威状态与保存/草稿协议已完整定义，NSDocument 默认行为需逐项绕过 | 最近打开/窗口恢复/文件协调改由三个独立系统 API 承担，不得缺失 |
| D11 | 判脏采用分块摘要树，同步精确判定 | 满足 E-04/AC-06，消除 checking 中间态导致的危险操作二选一 | 极端编辑模式下重算成本需实测，超预算时仅对 >5 MB 降级为有界等待的异步比较 |
| D12 | 渲染并发为每窗口 1／全应用 2，活动文档优先 | 单槽会造成跨窗口队头阻塞，使 P95 门槛不可达 | 并发数为待测工程起点，按实测调整 |

## 15. 残余风险与尚待确认事项

- 团队 Swift、Rust、Web、GPUI 的实际熟练度及可投入维护人数未知。
- 发行渠道、更新机制和 Intel 支持范围尚未确定；这些会影响签名、沙盒、测试矩阵和依赖选择。
- WebKit 分页输出、最低系统 TextKit 行为、所选解析器范围精度需要实测。
- GPUI 当前版本的组件、无障碍、WebView 嵌入和许可未核验，不据此作“已支持/不支持”的绝对断言。
- 外部不协作进程与特殊文件系统下无法凭普通路径检查承诺完全消除 TOCTOU，需记录支持范围并以失败保守处理。
- 操作系统故障、存储介质损坏和磁盘完全不可写不能由 UI 框架消除；恢复保证必须明确其失败边界。
- 原生 `RawHTMLSanitizer` 是本项目自实现的安全组件，缺少 DOMPurify 的长期公开审计历史。缓解措施：输入面限定为两类 AST 节点、白名单重建而非黑名单过滤、不确定即降级为转义文本、阶段 0 与 DOMPurify 双向对照、恶意夹具进入 CI 常态回归。该风险不因组件规模小而消失，须在评审中显式记录。
- D09–D12 均未经原型验证；阶段 0 实测与之冲突时以实测为准，并追加 ADR 记录反转理由，不得反向修改本文结论以迁就实现。

**最终判断：稳定可靠取决于状态不变量、事务、权限隔离和故障测试；易维护取决于减少无必要边界；可扩展取决于稳定接口，而不是选择最底层或最“高性能”的语言。当前需求下，原生主体与 Web 预览的组合最符合这三项共同目标。**
